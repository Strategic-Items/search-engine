# 38단계: 합성 질의 2,702개로 SPLADE를 다시 파인튜닝했다 (2026-10-01~02)

[35단계](../not-applied/stage-35-splade-domain-finetune.md)는 질의 108개로 PIXIE-Splade를 파인튜닝해 기준 모델을 넘지
못했다. 학습 신호가 약했던(손실이 5스텝 안에 0 근처로 떨어짐) 것이 원인으로 보였다. 이번에는
**어려운 질의만 25배 늘려** 같은 질문을 다시 확인했다. 원격 30B 모델로 질의를 만들고, 기준 모델이
쉽게 푸는 질의를 걸러냈다.

**결론부터.** 사전에 정한 채택 기준을 통과한 설정은 없다. 학습한 모든 설정이 **처음 보는 문서에서는
조금 오르고, 학습 문서군(docs_v2)에서는 내려간다.** 청크를 1위에 놓는 능력은 좋아졌지만 상위 5청크에서
더 많이 건지지는 못했고, dense와 합친 hybrid에서는 문서 단위 이득이 일관되지 않다. 학습한 SPLADE는
채택하지 않는다. 기준(학습하지 않은 `PIXIE-Splade-v1.5`)을 유지한다. 37단계의 새 카테고리 코퍼스(법령·고시,
행정·업무)에서도 같은 방향(SPLADE 단독에서 조금 오르고 청크 회수는 그대로)이 나왔으나 질의가 21~30개라 확정하지 못한다.

**코드 적용(2026-10-06).** 위 결론은 docs·core 검색 기준이다. 카테고리 검색(법령·고시, 행정·업무, 민원FAQ)에서는
**설정 C를 BM25 자리에 넣어 코드에 적용했다.** 카테고리 코퍼스에서는 SPLADE가 BM25보다 같은 창에서 높고
BM25가 청크 673개 인덱스에서 결과를 비우는 문제(37단계)도 없다(아래 "새 카테고리 코퍼스에서도 쟀다"). docs·core는 그대로 BM25다.
- **모델.** 설정 C 체크포인트를 저장소 밖(`~/models/splade-c`, 약 570MB)에 두고 `SEARCH_SPLADE_MODEL`로 가리킨다. 비워 두면 카테고리 검색도 BM25다.
  torch·transformers는 선택 의존성이다(`pip install .[sparse]`).
- **색인.** `law` 매핑(법령·행정·민원FAQ)에 `splade` `rank_features` 필드를 더했고, `search-index --dataset law|admin`을 모델이 설정된
  환경에서 돌리면 청크마다 SPLADE 벡터(상위 256 term, 가중치 0.01 이상, 문서 인코딩 256토큰)를 싣는다(`search_engine/sparse.py`, `indexer.py`).
  기존 인덱스는 이 필드가 없어 다시 색인해야 한다.
- **검색.** `retrieve()`에 `lexical="splade"`와 모드 `splade`를 더했다. 카테고리 비교 API(`POST /v1/categories/{id}/search/compare`)는 모델이 설정돼
  있으면 SPLADE·dense·hybrid(SPLADE+dense를 청크 단위 RRF k=60으로 합쳐 1위 청크의 95%로 컷오프, 청크 10·문서 5·문서당 6)를 돌린다.
  SPLADE 단독과 dense 단독은 문서 단위 경로를 쓴다(탐색기 표의 청크 컷오프 80%·93%는 서비스에 넣지 않았다).
- **확인.** 실험용 별칭에 행정·업무 183청크를 색인하고 실제 `retrieve()`로 30문항을 돌렸다. hybrid는 반환한 청크에 정답 청크가 든 질문이 27/30,
  평균 반환 청크 3.53개로 탐색기 오프라인 값(27/30, 3.33개)과 맞는다. 질의 후보 깊이가 서비스는 25개, 오프라인은 SPLADE 100·dense 50이라 약간 다르다.
  단위 테스트 267개 통과. 운영 별칭(`search-law`, `search-admin`)은 아직 다시 색인하지 않았다.

## 조건

**학습 데이터**

- **청크 풀.** docs 1,198 + core 3,956 = 5,154청크에서 다음을 뺐다. holdout 코퍼스는 과적합 측정용이라
  쓰지 않았다.
  - `data/queries_*.jsonl`의 근거 청크와 본문이 같은 사본(조각 60% 이상 공유): 148청크
  - 본문 200자 미만 228, 표 위주(표 줄이 50% 초과) 167
  - 남은 4,405청크 중 부모 4개(고시 개정 안내의 기술 사양 표)가 약 3,000청크라 **부모당 상한 100개**를
    두어 1,792청크로 줄였다(`scripts/splade_finetune_v2/select_pool.py`).
- **질의 생성.** 원격 vLLM의 `qwen3-vl-30b-a3b`(판정자·채팅이 쓰는 서버)로 청크마다 두 번 호출해 8개를
  만들었다(`gen_queries.py`). 첫 호출은 short·scenario·detail·why, 둘째는 colloquial·keyword·compare·
  procedure다. 프롬프트는 주제어를 반드시 넣고, 본문에 있는 숫자만 쓰고, 본문 문장을 베끼지 않고, 제목만으로
  답이 나오는 질문을 피하게 했다. 시험 8청크에서는 질문에 주제가 빠지거나 본문에 없는 숫자를 쓴 사례가
  있어 이 규칙을 넣었다.
- **질의 검증.** 같은 모델이 "본문만으로 답할 수 있는가, 질문만으로 주제가 드러나는가, 숫자·고유명사가
  본문에 근거하는가"를 판정하게 했고 셋 다 참인 질의만 남겼다. 통과율은 약 70%였다.
- **생성 범위.** 1,792청크 중 1,072청크(60%)에서 멈췄다(아래 운영 문제 참고). 질의 8개 × 1,072청크에서
  `keyword`(조사 없는 나열) 유형을 빼고 검증을 통과한 질의가 5,394개다.
- **난이도 선별**(`build_train.py`). 기준 모델 PIXIE-Splade로 5,394개 질의를 5,154청크에 채점해 정답
  순위를 구했다.

  | 정답(사본 포함) 순위 | 질의 수 | 처리 |
  |---|---:|---|
  | 1위 | 2,416 | 25%(540개)만 남김(망각 방지) |
  | 2~5위 | 1,275 | 사용 |
  | 6~50위 | 887 | 사용 |
  | 50위 밖 | 816 | 버림(라벨 오류나 지나친 난이도) |

  → **학습 예시 2,702개**(어려운 것 2,162 + 쉬운 것 540). 유형은 colloquial 458, scenario 473,
  detail 457, short 453, compare 407, procedure 233, why 221이다.
- **오답(hard negative).** 같은 채점에서 정답·사본이 아닌 상위 청크 30개를 후보로 두고, **평가 질의의
  근거 청크와 그 사본 146청크는 후보에서 뺐다.** 35단계의 오염을 되풀이하지 않기 위해서다.

**학습**(`train_v2.py`). `telepix/PIXIE-Splade-v1.5`에서 출발했다. 손실은
`CrossEntropy(질의·문서 내적) + λ·(FLOPS(질의) + FLOPS(문서))`이다. 배치 8, 질의마다 정답 1개와 후보 상위
15개 중 오답 1개, 같은 배치의 문서는 in-batch 오답으로 쓰고 정답 사본은 오답에서 가렸다. AdamW(weight
decay 0.01), 20스텝 워밍업 후 선형 감쇠, 문서 256토큰·질의 64토큰, 맥 M1 Pro MPS에서 1에폭(338스텝)을
돌렸다. 첫 스텝 손실이 1.7(35단계는 0.24)로 **배울 신호가 있는 데이터**다.

**평가.** 35·36단계와 같은 `scripts/evaluate_splade.py`(문서 256토큰, 상위 256 term, ratio 0.97)로 세
세트를 쟀다. 홀드아웃 규모 맞춤 코퍼스(2,178청크)와 검증 코퍼스(3,595청크, 36문항의 정답 부모와 사본에
홀드아웃 규모 맞춤 청크를 배경으로 더한 것)는 36단계와 같다.

**사전 채택 기준(결과를 보기 전에 고정).** 깨끗한 두 세트(holdout-small, 검증)의 P@1 합이 기준(61+30=91)보다
**3개 이상 높고**, docs_v2 P@1이 **129 이상**이면 후보로 본다. 통과해도 확정이 아니라 후보다. holdout과
검증은 학습 코퍼스와 문서가 겹치지 않고, docs_v2는 학습에 쓴 문서와 같은 문서군(평가 근거 청크만 제외)이다.

## 새 카테고리 코퍼스에서도 쟀다 (법령·고시, 행정·업무)

같은 기준 모델과 학습한 네 모델(A, C, D, E)을 이 코퍼스에서 같은 평가 스크립트로 쟀다(문서 256토큰, 상위 256

| 구성 | 문서 P@1 | 문서 Hit@5 | 문서 MRR | 청크 Hit | 청크 MRR | 1위 청크 적중 | 문서당 term |
|---|---:|---:|---:|---:|---:|---:|---:|
| dense(BGE)만 | 0.800 | 0.933 | 0.867 | 0.933 | 0.696 | 0.533 | - |
| SPLADE 기준 | 0.867 | 1.000 | 0.933 | 0.967 | 0.744 | 0.567 | 1,689 |
| SPLADE A | 0.900 | 1.000 | 0.944 | 0.967 | 0.751 | 0.600 | 1,091 |
| SPLADE C | 0.900 | 1.000 | 0.950 | 0.933 | 0.751 | 0.600 | 447 |

| SPLADE E | 0.900 | 1.000 | 0.950 | 0.933 | 0.736 | 0.600 | 892 |
| 기준 + dense | 0.833 | 0.900 | 0.867 | 0.967 | 0.676 | 0.467 | - |
| A + dense | 0.867 | 0.900 | 0.883 | 0.933 | 0.686 | 0.500 | - |
| C + dense | 0.900 | 0.900 | 0.900 | 0.933 | 0.701 | 0.500 | - |
| D + dense | 0.900 | 0.900 | 0.900 | 0.933 | 0.717 | 0.533 | - |

- **SPLADE 단독에서는 학습한 모델이 기준 이상이다.** 법령에서 C의 문서 P@1은 0.810 → 0.952(+3문항), 행정·업무에서는
  네 설정 모두 0.867 → 0.900(+1문항)이다. 1위 청크 적중도 두 카테고리에서 같거나 올랐다(법령 C·D 0.619 →
  0.714). **새 문서에서 조금 오른다는 앞선 패턴과 같은 방향**이다.
- **청크 Hit는 오르지 않았다.** 법령에서 0.762 → 0.810(+1문항)이고 행정·업무에서는 0.967 → 0.933(-1문항)이다.
  "1위로 올리지만 더 많이 건지지는 못한다"는 패턴도 같다.
- **dense와 합치면 이득이 줄거나 사라진다.** 법령에서 C + dense(0.905)는 C 단독(0.952)보다 낮고, 행정·업무의
  문서 Hit@5는 모든 hybrid에서 0.900으로 SPLADE 단독(1.000)보다 낮다. 이 코퍼스에서는 SPLADE 단독이
  hybrid보다 낫게 나온다. 37단계의 "dense를 더해도 차이는 1~2문항"과 방향이 같다.
- dense 단독(BGE)은 SPLADE보다 낮다(법령 P@1 0.810, 행정·업무 0.800).
- 학습한 모델의 문서당 term이 줄었다(법령 1,465 → 475~940, 행정·업무 1,689 → 447~892).
- **C가 가장 좋아 보이지만 확정하지 못한다.** C는 법령 SPLADE 단독에서 가장 높고(0.952), holdout-small(63)과
  검증(33)에서도 가장 높았다. 반면 docs_v2에서는 125로 가장 낮고, 세 세트 합은 기준과 같다(221 대 221).
  행정·업무에서는 네 설정이 같다. 질의 21~36문항에서 설정 네 개 중 좋아 보이는 것을 고르면 선택 편향이 생긴다.
- 한계: 질의가 적고 점검용이며(위), 평가는 오프라인이고 카테고리 경로의 운영 설정(컷오프, 필터)을 거치지
  않았다. 이 결과는 38단계의 "채택하지 않는다"를 뒤집지 않는다. 다만 카테고리 경로의 어휘 검색기로 **학습하지
  않은 SPLADE를 쓰는 것**이 우선이라는 점은 이 측정으로도 지지된다(SPLADE 기준이 dense와 hybrid보다 높다).

## 왜 학습했는데 낮아질 수 있나

**확인된 것**

- **학습 목표(청크)와 평가 목표(부모 문서)가 다르다.** 학습 예시의 hard negative 후보(상위 15개) 중
  **24.7%가 정답과 같은 부모 문서의 형제 청크**다(1순위 오답은 25.4%). 같은 문서의 청크는 주제와 용어가
  비슷한데 학습은 이것을 오답으로 가르쳤다. 모델은 문서 전체가 공유하는 단어의 가중치를 낮추고 그 청크에만
  있는 단어에 가중치를 몰아줄 수 있다. 청크 구분에는 유리하고 문서 단위 검색에는 불리하다.
- **학습이 문서 표현을 희소하게 만든다.** 문서당 활성 term이 1,458개에서 547~979개로 줄었다(정규화가
  없는 설정도 698, 842). 어휘 확장이라는 SPLADE의 장점이 줄어든다.

**추정(검증하지 않음)**

- 기준이 docs_v2에서 이미 130/135라 올릴 여지가 5문항, 잃을 여지가 130문항이다. 낯선 문서에서 오른 것은
  기준이 낮았기(88%, 83%) 때문이라는 설명과 맞는다.
- 합성 질의는 30B 모델의 문체로 균일하고 정답을 청크 하나로 가정한다. 이웃 청크가 사실은 관련 있는 경우가
  오답으로 학습된다.

## 운영 문제와 정정

- **죽은 연결.** 생성이 19:29부터 정체했다. 서버(vLLM)는 놀고 있었고 생성기가 끊긴 연결을 계속 붙잡고
  있었다. 연결 재사용을 끄고 타임아웃을 60초로 줄여 재시작했다.
- **맥 잠자기.** 노트북 덮개가 닫힌 상태에서 시스템이 유지 잠자기(Maintenance Sleep)에 들어가 프로세스가
  멈췄다 깨기를 반복했다. 학습·평가가 몇 시간씩 걸린 원인이다. `caffeinate -i`는 유휴 잠자기만 막는다.
  `caffeinate -s -i`(AC 전원일 때 시스템 잠자기 방지)를 추가한 뒤에는 새 잠자기 기록이 없었다.
- **생성 중단은 작성자(Claude)의 실수.** 기한을 거는 명령에서 맥의 `date` 문법(`-v+3H30M`)이 틀려
  기한 값이 비었고, 이것이 즉시 "기한 도달"로 처리되어 생성 프로세스를 1,072청크(60%)에서 종료시켰다.
  서버가 느려서 추가 생성량은 적었을 것이다.
- **MPS 메모리 부족.** 설정 B(2에폭)가 325/676스텝에서 MPS 메모리 17GB를 넘어 실패했다. 이후 설정에는
  40스텝마다 `torch.mps.empty_cache()`를 넣었고 D와 E는 완료됐다. B는 다시 돌리지 않았다.
- **요약 표시 버그.** 체인 로그의 설정별 한 줄 요약이 세 세트에서 같은 값으로 찍혔다(반복문 변수 오참조).
  평가 원자료와 최종 판정(`summarize.py`)에는 영향이 없다.

## 한계

- 표본이 작다(135, 69, 36문항). 1~5문항 차이는 노이즈일 수 있고 신뢰구간 검정은 하지 않았다.
- 질의 생성이 계획의 60%에서 멈췄다. 학습 곡선(데이터 50% 대 100%)은 하지 않았다.
- 설정은 네 개이고(B 실패) 학습률, 정규화, 에폭 외 변수(오답 후보 수, 배치 크기)는 바꾸지 않았다.
- 질의와 검증을 같은 30B 모델이 맡아, 검증이 생성의 편향을 걸러내지 못했을 수 있다.
- hybrid는 오프라인이며 BGE-m3-ko 하나로만 확인했다(Rune은 보지 않았다).

## 판단

**docs·core 검색에는 채택하지 않는다.** (카테고리 검색에는 위 "코드 적용"대로 설정 C를 쓴다.) 25배 많은 어려운 합성 질의로도 학습한 SPLADE가 학습하지 않은 PIXIE-Splade-v1.5를
일관되게 넘지 못했다. 청크를 1위에 놓는 능력의 개선은 의미 있는 신호지만, 우리가 쓰는 컨텍스트(상위 5문서의
청크)에 필요한 회수와 문서 단위 순위에는 이득이 없다.

다음에 시험할 수 있는 것:

1. **같은 부모의 형제 청크를 hard negative에서 제외**하고 다시 학습한다. 문서 단위 손실이 줄어드는지
   가장 직접적으로 가르는 시험이다(학습 50분, 평가 10분).
2. 문서당 term 수가 줄지 않도록 학습하거나(희소도 제약), 학습률을 더 낮춘다.
3. 학습 곡선(50% 대 100%)으로 데이터 양의 영향을 본다.

위 중 어느 것도 하지 않아도 이번 결론은 바뀌지 않는다. 36단계의 채택 전 남은 조건(같은 규칙 아래에서
hybrid 재비교, 전체 규모 확인, 미판정 청크 판정, 운영 경로 설계)이 더 우선이다.

## 재현

스크립트는 `scripts/splade_finetune_v2/`에 있다. 경로가 실험 환경(스크래치패드 `gen/`)에 박혀 있어 다른
환경에서는 고쳐야 한다. 생성 질의와 체크포인트, 평가 원자료는 스크래치패드에만 있고 저장소에는 넣지 않았다.

```bash
./run_all.sh                          # 생성 종료 후 선별·기준 평가·학습 A,B,C·평가·요약(summarize.py)
./run_more.sh                         # λ=0 설정 D,E(+ RESULTS2.md)
python hybrid_ft.py bge               # SPLADE+dense hybrid 표(문서·청크)
```
