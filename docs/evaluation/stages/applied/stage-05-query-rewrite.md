# 5단계: 질의 재작성 융합

4단계 뒤 남은 문서 실패 6건은 전부 표현 변경형이었다. 질문은 "업체의 약속 문서"라고
하는데 고시는 "수출자 서약서"라고 쓰고, "관청에 알리는 서류"는 서식에서 "지위승계
통지서"다. 구(句) 단위 개념 치환이라 동의어 사전으로는 닿지 않는다
([동의어 기록](../../../design/synonyms_v1.md)의 75건 중 1건이라는 결과가 그 한계다).

`OLLAMA_CHAT_MODEL`로 질문을 검색어로 다시 쓰고, **원본과 재작성을 모두 검색해 순위를
가중 RRF로 합친다.** 재작성이 원본을 대체하지 않는다는 점이 핵심이다.

## 재작성만으로는 더 나쁘다

세 가지를 같은 v2 세트로 측정했다(BM25, 깊이 5, 재작성 1회씩).

| 전략 | Hit@1 | 문서 Recall@5 |
|---|---:|---:|
| 원본만 | 72.5% | 85.0% |
| **재작성만** | **70.0%** | **83.8%** |
| 원본 + 재작성 융합 1:1 | 75.0% | 87.5% |
| 원본 + 재작성 융합 1:0.5 | 72.5% | 87.5% |

qwen2.5:3b는 도메인 용어를 모른다. 재작성 결과에 `특허공여제`(001), `사업이전신고서`(004)
처럼 존재하지 않는 용어를 만들어 넣었고, 중국어 글자가 섞여 나온 사례도 있었다. 그래서
재작성을 원본보다 낮은 가중치로만 반영한다. 기본값 `SEARCH_QUERY_REWRITE_WEIGHT=0.5`는
재작성이 문서를 **추가**할 수는 있어도 원본의 1위를 밀어낼 수는 없게 한다.

## 버린 대안: 1차 검색 제목으로 접지

재작성 프롬프트에 1차 BM25의 후보 문서 제목을 넣어 실제 코퍼스 어휘에 접지시키는 방법을
시도했다. 결과는 더 나빴다(문서 Recall@5 85.0% → 80.0%, 지연 2배). 모델이 후보 제목
하나를 그대로 베끼는데, 1차 검색이 틀렸을 때 그 오류를 그대로 고착시킨다. 001과 012가
이렇게 정답을 잃었다. 재작성이 필요한 질문이 바로 1차 검색이 실패한 질문이므로 이 방향은
구조적으로 맞지 않는다.

## 대가

| | 4단계 | 5단계 | 차이 |
|---|---:|---:|---:|
| BM25 Hit@1 | 72.5% | 77.5% | +5.0%p |
| BM25 문서 Recall@5 | 85.0% | 87.5% | +2.5%p |
| BM25 근거 Recall@5 | 70.0% | 72.5% | +2.5%p |
| 하이브리드 문서 Recall@5 | 67.9% | 77.9% | +10.0%p |
| BM25 p50 | 15.8ms | 605.5ms | **38배** |

40문항 기준 +2.5%p는 한 문항이다. Hit@1의 +5.0%p가 두 문항이다. 반면 검색은 15ms에서
0.6초가 된다. 그리고 지금까지 어휘 검색 경로에는 LLM 의존성이 아예 없었는데, 이 기능은
모든 검색을 `OLLAMA_CHAT_MODEL`에 묶는다. 그래서 **기본값은 꺼짐**이다.

모델을 부르지 못하면 원본 질의만으로 검색해 결과를 좁힐 뿐 요청을 실패시키지 않는다.
다만 `--rewrite` 평가 실행은 예외로 실패시킨다. 재작성이 조용히 빠진 비교는 측정하려던
것을 측정하지 않기 때문이다.

재작성은 어휘 검색에만 쓰인다. dense 경로는 질의 임베딩을 쓰므로 5단계에서 dense 단독
지표는 4단계와 같다.
