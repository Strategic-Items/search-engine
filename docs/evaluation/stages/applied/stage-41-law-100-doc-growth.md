# 41단계: 법령·고시 코퍼스가 50건에서 100건으로 늘어, 새 50건으로 질문 50개를 더 써서 100문항으로 다시 쟀다 (2026-10-06)

파서 쪽(`unstructured-doc-parser_ver2`, 커밋 `f06c639`)이 `01_법령고시`에 50건을 더 넣어 100건(청크 4,633개)이 됐다.
`search-law` 인덱스는 아직 옛 50건(청크 2,160개)을 읽고 있었으므로 먼저 `search-index --dataset law`로 다시
색인했다(100건 전부 반영 확인). 그다음 새로 들어온 50건 본문을 보고 질문 50개를 더 써서(`law50`과 같은 방식)
기존 50문항에 더해 100문항으로 다시 쟀다. 서비스 설정은 바꾸지 않았다.

**결론부터.**
- **새 문서 50건은 모두 1문항 이상으로 덮였다.** `build()`가 정답 청크를 못 찾은 질문은 없었다(100/100 통과).
- **서비스 경로(SPLADE 어휘 + 청크 우선 + 청크 컷오프 0.95)의 hybrid는 청크 Recall 0.910, Precision 0.558(최대 0.720),
  평균 3.4청크, 문서 Hit 97/100이다.** 컷오프를 걸지 않으면 같은 hybrid가 Recall 0.940, Precision 0.235(평균 9.8청크)라
  Precision이 낮게 보인다. 성능은 컷오프를 건 값으로 읽는다.
- 컷오프를 올릴수록 Precision이 오르고 Recall이 내린다: 0.9에서 0.920/0.415, 0.97에서 0.870/0.615, 0.99에서 0.860/0.687
  (표는 아래). 37단계 21문항 점검용 질문(0.905)보다 낮은 것은 같은 조항의 다른 판이 코퍼스에 더 많이 섞였기 때문으로 보인다.
- 컷오프 0.95에서 놓친 질문은 9개다. 정답 문서 안에서 정답 청크가 잘린 경우와 정답 문서를 놓친 경우가 섞여 있고, 몇 개를
  열어 본 범위에서는 상위에 뜬 청크가 "같은 질문에 답이 되는 다른 판"인 경우가 있었다(라벨은 한 곳으로 고정).
- **반복해서 걸리는 질문(001, 020, 080, 087 등)은 37단계에서 이미 적은 "같은 조항이 여러 판에 있다" 문제의
  재현이다.** 새로 들어온 50건 다수가 옛 개정문·신구대비표·행정예고라서, 한 조항의 역대 판이 코퍼스에 더 많이
  쌓였다. 몇 개를 열어 확인한 범위에서는(전부는 아니다) 상위에 뜬 문서가 "오답"이 아니라 "같은 질문에 답이 되는
  다른 판"이었다. 라벨은 가장 최신 판 한 곳으로만 고정했다.
- 운영 기본값(컷오프, 후보 수, SPLADE 모델)은 바꾸지 않았다. `search-law` 색인만 100건으로 갱신한 채 남는다.

## 조건

**입력.** `SEARCH_LAW_SOURCE`(`unstructured-doc-parser_ver2/data/category_chunks/01_법령고시/docs.jsonl`)가 고정
경로라 코드 변경 없이 100건을 그대로 읽는다. 늘어난 50건은 `git show f06c639^:...docs.jsonl`과 현재 파일을 문서
id 집합으로 비교해 찾았다(50건 추가, 0건 삭제).

**색인.** `.venv/bin/search-index --dataset law`. SPLADE 인코딩에 필요한 `torch`·`transformers`가 `.venv`에
없어서 `pip install -e ".[sparse]"`로 더했다(전에는 `search-engine/venv`를 따로 썼다 — 37·38단계).
전 인덱스 `search-law-v20261006080241-ac399d`(2,160청크, 옛 50건)에서 새 인덱스
`search-law-v20261006084443-02b5ec`(4,633청크, 100건)로 별칭을 옮겼다.

**질문 셋.** `data/queries_law100_v1.jsonl` 100문항 = 기존 `law50_specs.py` 50문항(law50-v1-001~050) + 새
`law100_specs.py`의 `NEW_SPECS` 50문항(law100-v1-051~100, 새로 들어온 50건에 문서당 1문항). 유형은 natural
30, identifier 15, annex 4, compare 1. 방식은 37·법령50단계와 같다 — 질문마다 필수 구절을 적고, 그 구절을 모두
담은 청크를 코드가 정답으로 해석한다(`SPECS=law100 scripts/law/evaluate_law.py --build`). **정답을 아는 사람
(Claude)이 본문을 보고 쓴 질문이라 점검용이고 성능 판단용이 아니다.**

**측정 조건.** 서비스 카테고리 경로(`routes.py`)와 같은 옵션: `lexical=splade`, 청크 우선, 청크 컷오프 비율 `search_category_cutoff_ratio`
(기본 0.95). 상위 5문서, 문서당 최대 6청크, LLM 청크 필터·답변 가능성 판정 끔, 절대 하한 0. 비율은 환경변수 `CUTOFF`로 바꾼다.
`splade`(0.80)·`dense`(0.93) 단독 모드는 탐색기에서 정한 비율을 검색기 청크 점수에 건다(`single_window`). bm25는 38단계부터 카테고리 검색에서 뺐다.

새로 쓴 질문인데, 대외무역법·전략물자수출입고시의 자율준수무역거래자·우려거래자 조문이 역대 개정(신구대비표,
입법예고, 공고문)에 여러 번 나와 같은 문제가 재현된다. 새로 들어온 50건 중 다수가 이런 역대 개정문·신구대비표라서
코퍼스가 늘수록 이 문제가 더 자주 걸릴 것으로 보이지만, 100문항 전부를 열어 확인하지는 않았다.

## 한계

- 질문 100개 중 50개(새 문항)는 이번에 처음 썼고, 사람 교차검수는 하지 않았다.
- "같은 조항이 여러 판에 있다" 진단은 공통으로 걸린 질문 몇 개를 읽은 범위이고, 전체 29개 미스를 전수 확인하지
  않았다. 몇 개는 순수한 라벨 한계(가장 최신 판만 정답으로 고정)가 아니라 검색이 최신 판을 못 앞세운 것일 수
  있으나 가리지 않았다.
- 컷오프·후보 수·SPLADE 설정은 37~40단계 값을 그대로 썼고 100건 코퍼스에 맞춰 다시 고르지 않았다.
- `doc_status`(안/개정/확정)·`superseded_by` 같은 최신 판 우대 신호는 카테고리 인덱스에 아직 없다(37단계에서도
  같은 한계를 적었다). 코퍼스가 늘면서 이 공백의 영향이 커지는 것으로 보인다.

## 재현

```bash
.venv/bin/pip install -e ".[sparse]"                                        # torch·transformers (SPLADE 색인용)
.venv/bin/search-index --dataset law                                        # 100건 재색인

  .venv/bin/python scripts/law/evaluate_law.py --build                      # 100문항 질문 셋 생성·검증
SPECS=law100 QUERIES_FILE=data/queries_law100_v1.jsonl \
  .venv/bin/python scripts/law/evaluate_law.py                              # splade·dense·hybrid 채점
```
