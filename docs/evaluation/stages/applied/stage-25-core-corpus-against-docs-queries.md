# 25단계: core를 docs 질의셋에 섞으면 무엇이 깎이고, 왜 깎이는가 (2026-09-22)

지금까지 docs-v2 측정은 `search-docs-only` 하나만 읽었다. 운영은 `core,docs`가
기본값이므로(`.env.example`), 두 코퍼스를 함께 읽을 때 지금 지표가 유지되는지
재지 않은 채로 있었다.

이 단계는 네 번에 걸쳐 진행됐다. **얼마나 깎이는지**를 재고, **청킹 규약을 맞추면
회복되는지**를 보고, **그 하락이 라벨 한계는 아닌지**를 검증하고, 마지막으로
**왜 깎이는지**를 찾았다. 앞의 셋에서 세운 설명은 대부분 마지막에 기각됐다.
기각된 것도 함께 남긴다 -- 어디를 이미 파봤는지가 다음 사람에게 필요하다.

**결론부터.** 손해의 원인은 코퍼스의 성질(길이·제목·문서 수)이 아니라 **합치는
방식**이었다. 별칭 두 개를 한 질의로 던지면 IDF와 평균 문서 길이가 인덱스마다
따로 계산되어, 두 코퍼스가 서로 다른 자로 채점된 채 한 순위표에 섞인다.

> **현재 상태 (2026-09-29 기준).** 아래 본문은 2026-09-22 측정 기록이라 그대로 두었다.
> 이 문서가 세운 두 처방 -- 다중 인덱스 `dfs_query_then_fetch`와 `title^3` → `title^1` --
> 은 이후 코드에 반영됐다(`af064c9`, 2026-09-24. 근거는 [26단계 후속 확인](../not-applied/stage-26-holdout-overfitting-check.md),
> [28단계](stage-28-title1-dfs-ranker.md)). 이 단계에서 코드에 남은 것은 그 두 처방과
> 청크 번호 기점 규약(`identity.py`)이다. 재청킹은 채택하지 않았다. 「판단」의
> "처방을 아직 적용하지 않았다"와 「다음 순서」는 작성 시점의 서술이며, 항목별 현재
> 상태는 「다음 순서와 현재 상태」에 옮겼다.

## 조건

코퍼스와 질의셋은 기존과 같다. docs 1,198청크(`review-corpus/docs.jsonl`),
core 3,956청크, 질의 `data/queries_docs_v2.jsonl` 135문항. 검색기·모드·컷오프·
임베딩 모델은 모두 그대로이고 **읽는 별칭만** 다르다.

| 별칭 | 무엇 |
|---|---|
| `search-docs-only` | docs만 |
| `search-documents` + `search-docs-only` | core+docs (운영 기본값) |
| `search-documents-trim` | core에서 청크가 폭주한 부모 4건만 뺀 926청크 |
| `search-documents-rechunk` | core를 docs 규약으로 다시 자른 13,030청크 |

세 실행 모두 `gold_missing_from_index`가 0이므로 **아래 하락은 전부 순위 문제다.**

두 가지 지표를 쓴다. 표에 **근거 Recall@5** 계열이 나오면 `search-evaluate`의
주 지표이고(23단계), **1위 적중**이 나오면 원인 분석용으로 **컷오프를 끈 상태의**
1위 문서 적중(135문항)이다. 컷을 꺼야 순위 문제와 절단 문제가 갈린다.

## 왜 core 질의셋으로 재지 않았나

core에도 자체 질의셋 `data/queries_v1.jsonl` 93문항이 있지만 이 비교에 쓸 수 없다.

| | `queries_v1` (core) | `queries_docs_v2` (docs) |
|---|---|---|
| `gold` | 있음 (parent_id) | 있음 (parent_id) |
| `gold_groups` | 없음 | 있음 |
| `evidence_groups` | **없음** | 있음 |
| `evidence_requirements` | **없음** | 있음 |
| `answerable` | 없음 | 있음 |

`evidence_groups`가 없으면 23단계가 주 지표로 올린 근거 청크 지표가 계산되지
않는다. 게다가 93문항 전부에 `review_status: needs_co_gold_review`가 붙어 있고,
`gold_basis`는 "기존 FAQ 207건 수작업 라벨"이다. 코퍼스가 넓어지면 공동 정답을
다시 봐야 한다고 라벨 스스로 예고해 둔 상태다.

그래서 이 측정은 **라벨을 손대지 않고** docs 질의셋을 그대로 던져, core가 방해물로
들어왔을 때 docs 정답을 여전히 위로 올리는지만 본다. 노이즈 내성 측정이다.
**core 문서를 얼마나 잘 찾는지는 이 단계에서 재지 않는다.**

## 1. 얼마나 깎이는가

| 지표 | docs만 | core+docs | trim+docs | 재청킹+docs |
|---|---:|---:|---:|---:|
| **근거 Recall@5** | **0.9630** | 0.9111 | 0.9222 | 0.8815 |
| **근거 모든 근거@5** | **0.9481** | 0.9037 | 0.9111 | 0.8741 |
| **근거 MRR@5** | **0.8179** | 0.7446 | 0.7742 | 0.7316 |
| 근거 Precision@5 (하한) | 0.2635 | 0.2177 | 0.2492 | 0.1990 |
| 평균 반환 청크 | 5.78 | 6.83 | 5.64 | 7.59 |
| 문서 P@1 | 0.9481 | 0.8444 | 0.8889 | 0.8370 |
| 문서 Recall@5 | 0.9031 | 0.8599 | 0.8747 | 0.8265 |
| 평균 반환 문서 | 1.19 | 2.07 | 1.50 | 2.39 |
| 첫 결과 적중 | 128 / 135 | 114 / 135 | 120 / 135 | 113 / 135 |

유형별 첫 결과 적중:

| 유형 | 질의 | docs만 | core+docs | trim+docs |
|---|---:|---:|---:|---:|
| paraphrase | 34 | 32 | 25 | 28 |
| scenario | 68 | 66 | 60 | 63 |
| multi_evidence | 18 | 18 | 17 | 17 |
| identifier_number | 6 | 6 | 6 | 6 |
| identifier_mixed | 5 | 5 | 5 | 5 |
| identifier_article | 4 | 1 | 1 | 1 |

**core를 섞으면 근거 Recall@5가 0.9630 → 0.9111로 5.2p 떨어진다.** 식별자 구간은
꿈쩍하지 않는다 -- 공고번호 필터가 두 검색기에 걸려 있어서다. 손해는 전부
자연어 질의(`paraphrase`, `scenario`)에서 난다.

## 2. 기각된 설명 넷

### 청크 폭주는 눈에 띄지만 주범이 아니다

core 인덱스는 부모 612건에 청크 3,956개인데 분포가 고르지 않다.

| 청크 수 | 부모 문서 |
|---:|---|
| 1,268 | `yestrade-notice-21177` (제37차 전략물자수출입고시 개정 안내) |
| 636 | `yestrade-notice-23257` |
| 630 | `yestrade-notice-22867` |
| 496 | `yestrade-form-23302` |
| 나머지 608문서 | 합계 926 |

**상위 4개 문서가 core 전체 청크의 77%를 차지한다.** 공지 한 건에 별지 서식 전체가
첨부로 딸려 들어가 잘게 쪼개진 것이다. 그런데 이 4건을 빼도(`trim`) 근거 Recall@5는
0.9111 → 0.9222에 그친다. 하락폭 −5.2p 중 **−1.1p만 이 4건 탓이고 −4.1p는 나머지
608문서가 낸다.**

나중에 컷오프를 끄고 가해 문서를 전수로 세어 보면 더 분명하다. gold보다 위에 올라온
문서 **119건 중 거대 문서는 1건(1%)**뿐이고, 특정 문서가 몰아치지도 않는다(최다
가해 문서 4회). 손해는 600여 문서의 긴 꼬리에서 난다.

### core 재색인은 아무것도 바꾸지 않는다

24단계에서 내려받기 사본 제거와 시점 힌트를 `prepare`에서 `indexer`로 옮겼으므로
core 색인이 그 이전 것이라 불리하게 나왔을 가능성을 확인했다. 아니었다.
`search-prepare`를 다시 돌려도 `core.jsonl`의 sha256이 같고, 새 `parent_identity()`를
core에 걸면 **사본 0건**이다. core 3,956청크는 `source_path`가 전부 비어 있는데,
`download_copies`는 `... (1).hwp` 같은 파일명을 보고 판정하기 때문이다.
**사본 제거는 docs 코퍼스 전용 장치다.**

### 컷오프는 범인이 아니다

`cutoff_ratio=0`으로 절단을 완전히 꺼도 1위 적중이 똑같이 떨어진다.

| | docs만 | core+docs | 재청킹+docs |
|---|---:|---:|---:|
| 컷오프 켬 | 126 | 109 | 99 |
| 컷오프 끔 | 126 | 109 | 99 |

gold는 후보 안에 있다(134/135, 133/135). **core 문서가 진짜로 이긴다.**

### 시점 부스트 비대칭은 상관이었지 인과가 아니다

연도를 대는 질의는 `published_at`에 가중치 6을 준다. 자격이 크게 비대칭이다.

| 인덱스 | published_at | period_hint |
|---|---:|---:|
| docs | **32%** | **0건** |
| core | 93% | 0건 |

docs를 보상하려고 24단계가 만든 `period_hint`가 배포된 docs 인덱스에 하나도 없다
(인덱스는 2026-09-18, 기능은 2026-09-22 커밋). 손해도 그 구간에 몰려 보인다
(시점 부스트가 걸리는 질의 −15.3%p 대 안 걸리는 질의 −9.5%p).

**그런데 부스트를 통째로 꺼도 순위가 전혀 바뀌지 않는다**(109 → 109). 부스트는
덧셈으로 들어가는데 융합이 점수가 아니라 순위(RRF)로 이뤄지므로 웬만해서는 순서를
뒤집지 못한다. 연도를 대는 질의가 곧 출처를 지목하는 질의라서 겹쳐 보였을 뿐이다.

## 3. 청킹 규약을 맞춰도 회복되지 않는다

두 코퍼스의 청크는 실제로 다른 물건이었다.

| | core (기존) | docs |
|---|---:|---:|
| 청크 본문 길이 중앙값 | **2,396자** | **627자** |
| 길이 분포 | p25 2,391 · max 2,399 — 글자수 고정 슬라이스 | p25 392 · max 827 — 구조 기반 |
| 부모당 청크 | 6.5 | 23.0 |
| 청크 제목 | 부모당 항상 동일 (다청크 부모 85건 전부) | 27/49 부모가 섹션 제목을 붙여 청크마다 다름 |
| `chunk_index` 기점 | **1** | **0** |

23단계가 청크를 채점 단위로 세웠으므로, 한 인덱스에서 같이 읽는 두 코퍼스의 청크가
3.8배 다르면 그 자체가 결함이다. core를 docs에 맞췄다.

**재청킹.** core는 yestrade 수집 단계에서 2,400자 고정 슬라이스(겹침 ~180자)로 잘려
들어온다. 고정 슬라이스는 연속이므로 겹침을 걷어내면 원문이 복원된다(부모 613건 전부
`chunk_index` 1..n 연속, 경계 겹침 179~180자로 확인). 그 위에 docs와 **같은 청커·같은
파라미터**를 걸었다 -- `scripts/rechunk_core.py`.

| | 기존 | 재청킹 | docs |
|---|---:|---:|---:|
| 청크 | 3,956 | 13,030 | 1,198 |
| 부모 | 612 | 612 | 52 |
| 본문 총 글자 | 8,292,599 | 8,292,599 | 664,606 |
| 부모당 청크 | 6.5 | 21.3 | 23.0 |
| 청크당 글자 | 2,137 | 636 | 555 |

청크가 3.3배가 된 것은 내용이 아니라 해상도가 바뀐 것이다. core 본문은 원래 docs의
12.5배다.

**청크 번호 규약도 같이 고쳤다.** `prepare`와 `indexer` 양쪽에 "첫 청크"를
`if not row["chunk_index"]`로 찾는 코드가 있었다. core는 1부터 매기므로 이 조건이
한 번도 참이 되지 않아 **612개 문서 전부 앞머리(`head`)가 빈 문자열**이었다. 24단계가
넣은 시점 힌트가 core에 0건이었던 진짜 이유가 여기 있다. 기점을 0으로 고정해
`identity.py`로 올리고, 어긋나면 `prepare`가 멈추게 했다.

**맞추지 못한 것은 제목이다.** 재청킹해도 613부모 중 11개만 청크별 제목이 생겼다.
core 본문은 마크다운 헤더가 **0%**다(44.6%는 `1. `로 시작하는 목록 항목이지 절 제목이
아니다). docs가 청크마다 제목을 갖는 것은 HWP/PDF 파서가 헤더를 만들어주기 때문인데,
core는 yestrade에서 평문으로 크롤링해 온 것이라 헤더가 애초에 없다.

```text
yestrade-notice-21177#0001  "첨부 내부 파일: 업로드파일20260201/...[별지 14]...docx"
```

첨부 파일을 파서에 태우지 않고 텍스트로 긁어온 흔적이다. 제목 규약을 맞추려면 core
수집 경로를 바꿔야 하므로 이 단계 밖이다. `1. ` 같은 목록 번호를 제목으로 지어내지는
않았다 -- 제목은 본문의 3배로 가중되고 임베딩 입력에도 들어간다.

**결과는 더 나빴다.** 근거 Recall@5가 0.9111 → 0.8815로 3.0p 더 떨어진다(위 1절 표).
거대 문서는 오히려 세졌다 -- `yestrade-notice-21177`이 1,268 → **4,446청크**가 됐고,
4건의 비중이 77% → **84%**로 늘었다.

**이 결과는 아래 5절이 뒤집는다.** 채점이 망가진 상태에서만 나타나는 현상이었다.

## 4. 하락은 라벨 한계가 아니다

`queries_docs_v2`의 gold는 docs만 보고 매겨졌다. 매니페스트가 그렇게 적고 있다.

```
source_corpus: data/generated/docs-v2/review-corpus/docs.jsonl
source_chunks: 1198     total_source_parents: 52
human_review: "pending"
```

core 612부모는 정답이 될 자격이 없었다. core 문서가 1위를 하면 질문에 답하든 말든
오답으로 채점된다. 1위를 잃은 24건을 전수 판정했다.

판정은 두 가지를 기계로 갈랐다. **하나, 질의가 출처를 지정하는가.**
`"2006년 자료에서는"` 처럼 자료를 지목하는 질의가 24건 중 9건이다. 이런 질의에
내용만 같은 다른 문서는 공동 정답이 아니다. **둘, 승자가 gold와 같은 문서인가**
(12자 shingle 겹침).

| 판정 | 건수 | qid |
|---|---:|---|
| **라벨 누락 확정** | **2** | 018, 020 |
| 진짜 오답 | 22 | 나머지 |

라벨 누락 2건은 **core가 docs와 같은 서식을 중복 보유**한 경우다.

| core 사본 | 청크/글자 | docs 원본 | 청크/글자 |
|---|---:|---|---:|
| `yestrade-form-22209` | 3 / 1,187 | 별지16 사전거래보고서 | 3 / 1,660 |
| `yestrade-form-23307` | 3 / 1,510 | annexeds02_2 | 5 / 2,675 |

`docs-v2-018`은 "거래 내역 칸을 언제 채우냐"를 묻고 core 사본이 `□ 거래 내역
(※ 수출 후 작성 필요)`를 그대로 담고 있다. 24단계의 사본 제거는 파일명을 보므로
**코퍼스를 가로지르는 중복은 잡지 못한다.**

**의심 둘은 기각됐다.** `identifier_article` 4문항이 25단계부터 1/4로 바닥이라 gold를
의심했는데, 근거를 직접 읽으니 전부 정확하다 -- 별지16 서식 본문에
`제54조(상황허가의 면제)`와 `제26조(개별수출허가의 면제)`가 그대로 있고, 130의 gold도
`법 제19조의3 및「전략물자 수출입고시」제54조`를 담고 있다(그 질의의 승자
`law-gosi-015`는 제15조라 아예 다른 조문이다). 또 core 사본이 정답이라는 판정도 둘은
기각됐다 -- 겹침은 높지만 core 쪽이 껍데기다.

| core 사본 | 글자 | docs 원본 | 글자 |
|---|---:|---|---:|
| `yestrade-board-67-1284` | **965** | 전략기술의 무형이전 통제 | **19,266** |
| `yestrade-board-67-1461` | **117** | 한미양해각서11 | **7,607** |

라벨을 고쳐 다시 재면 **재청킹 조건만 0.8741 → 0.8815로 0.7p 오르고** docs만과
core+docs는 꿈쩍하지 않는다. 그 두 조건에서는 core 사본이 애초에 1위를 하지 않았다.

**하락의 대부분은 진짜 검색 실패다.**

## 5. 원인: 어휘 검색기가 두 인덱스에서 무너진다

검색기별로 가르니 한쪽만 무너진다.

| 검색기 | docs만 | core+docs | 손해 |
|---|---:|---:|---:|
| **bm25** | 122 | **63** | **−59** |
| vector | 130 | 121 | −9 |
| hybrid (현행) | 126 | 109 | −17 |

벡터는 거의 멀쩡한데 BM25가 반토막 난다. 하이브리드가 −17인 것은 RRF가 **망가진
목록을 멀쩡한 목록과 반반 섞기 때문**이다. 지금 상태에서는 **벡터 단독(121)이
하이브리드(109)보다 낫다.** 어휘 쪽을 고치기 전까지 융합은 손해다.

원인은 합치는 방식에 있다. `Settings.document_aliases`는 별칭 두 개를 쉼표로 이어
한 질의로 던지는데, 검색이 `search_type`을 지정하지 않아 기본값 `query_then_fetch`를
쓴다. 이것은 **IDF와 평균 문서 길이를 인덱스마다 따로** 계산한다. 두 코퍼스의 BM25
점수는 서로 비교 불가능한 채 한 순위표에 섞인다.

| 용어 | docs 내 빈도 | core 내 빈도 | 차이 |
|---|---:|---:|---:|
| 러시아 | 0.42% | 5.54% | **13배** |
| 반도체 | 3.92% | 12.49% | 3.2배 |
| 수출 | 22.70% | 20.85% | 비슷 |

같은 용어가 한쪽에선 희귀어, 다른 쪽에선 흔한 말로 채점된다. 길이 정규화도 같은
문제를 갖는다 -- core 청크 2,396자는 core 평균(2,137자) 기준으로는 페널티를 거의
받지 않지만 docs 평균(555자) 기준이라면 크게 받는다. **긴 청크가 용어는 많이 물면서
페널티는 피한다.**

전역 통계(`dfs_query_then_fetch`)로 바꾸면 회복된다.

| 검색기 | 인덱스별 IDF | 전역 IDF |
|---|---:|---:|
| bm25 | 63 | **92** |
| hybrid | 109 | **114** |

`docs만`은 126 → 126으로 변하지 않는다. 인덱스가 하나라 바뀔 것이 없다 -- 대조군이
기대대로 움직인다.

## 6. 제목 증폭기: 재청킹의 추가 손해는 이것이었다

| 조건 | title^3 (현행) | title^1 | 제목 없음 |
|---|---:|---:|---:|
| core+docs | 109 | 112 | 111 |
| 재청킹+docs | **99** | **110** | 104 |

core 청크는 부모당 제목이 하나인데 제목은 본문의 3배로 가중된다. 청크를 3.3배로
쪼개면 그 제목이 3.3배로 증폭된다. 재청킹 조건에서만 11건이 회복되는 이유다.

## 7. 둘을 같이 걸면 3절의 결론이 뒤집힌다

| 조건 | 기본 | +전역 IDF | +전역 IDF +title^1 |
|---|---:|---:|---:|
| docs만 (기준) | 126 | 126 | — |
| core+docs | 109 | 114 | **119** |
| 재청킹+docs | 99 | 112 | **118** |

BM25만 따로 보면 더 분명하다.

| 조건 | 인덱스별 IDF | 전역 IDF |
|---|---:|---:|
| core+docs | 63 | 92 |
| 재청킹+docs | **49** | **91** |

재청킹은 기본 상태에서 49로 core+docs(63)보다 나쁘지만, 전역 IDF를 걸면 91 대 92로
같아진다. **3절의 "재청킹이 더 나쁘다"는 채점이 망가진 상태에서만 나타나는
현상이었다.** 청크를 잘게 쪼개면 제목 증폭도, 인덱스별 IDF 왜곡도 함께 커지기
때문이다. 두 처방을 걸면 119 대 118로 사실상 같다.

## 판단

**운영 기본값을 이 결과만으로 바꾸지 않는다.** 이 측정은 docs 질의셋에 대한 노이즈
내성만 봤고, core를 넣는 이유인 "core 문서를 잘 찾는가"는 재지 않았다. 한쪽만 재고
기본값을 정할 수는 없다. 그리고 아래 처방들은 이 문서를 쓴 시점에는 아직 적용하지
않았다(이후 반영됐다. 문서 맨 위 「현재 상태」 참조).

확정된 것은 일곱이다.

1. core를 섞으면 docs 질의 근거 Recall@5가 0.9630 → 0.9111로 **5.2p 떨어진다.**
   정답은 전부 색인 안에 있으므로 순위 문제다.
2. **손해는 어휘 검색기에서만 난다.** 벡터 −9, BM25 −59. 하이브리드가 −17인 것은
   RRF가 망가진 목록을 섞기 때문이고, 지금은 벡터 단독이 하이브리드보다 낫다.
3. **기술적 원인은 인덱스별 IDF·평균 길이다.** 전역 통계로 bm25 +29, hybrid +5.
4. **제목 증폭기는 실재하나 재청킹 조건에서만 크다**(+11).
5. 두 처방을 합치면 −17이 −7로 줄고, **재청킹과 기존 청킹의 차이는 사라진다.**
6. 하락은 라벨 한계가 아니다. 1위를 잃은 24건 중 22건이 진짜 오답이고, 라벨을
   고쳐도 0.7p뿐이다.
7. 컷오프·거대 문서·시점 부스트·청크 길이는 **전부 기각됐다.**

남은 −7(126 대 119)은 이 문서를 쓴 시점에는 설명되지 않았다. 이후에도 원인을 따로
분해한 측정은 없다(아래 4번).

## 재현

```bash
# 세 API를 같은 코드로 띄우고 별칭만 달리한다
SEARCH_DOCUMENT_DATASETS=docs \
  .venv/bin/uvicorn search_engine.api:app --host 127.0.0.1 --port 8101
SEARCH_DOCUMENT_DATASETS=core,docs \
  .venv/bin/uvicorn search_engine.api:app --host 127.0.0.1 --port 8102

# core를 docs 규약으로 다시 자른 별도 별칭
python scripts/rechunk_core.py <corpus_project_v1.jsonl> <out.jsonl> \
  --parser-src ../unstructured-doc-parser_ver2/src
.venv/bin/search-prepare <out.jsonl> --out <prepared>
SEARCH_INDEX_ALIAS=search-documents-rechunk SEARCH_INDEX_PREFIX=search-documents-rechunk-v \
  .venv/bin/search-index <prepared>/core.jsonl --dataset core --manifest <prepared>/manifest.json
SEARCH_DOCUMENT_DATASETS=core,docs SEARCH_INDEX_ALIAS=search-documents-rechunk \
  .venv/bin/uvicorn search_engine.api:app --host 127.0.0.1 --port 8104

# 같은 질의셋을 각 포트에
.venv/bin/search-evaluate data/queries_docs_v2.jsonl \
  --base-url http://127.0.0.1:8101 \
  --prepared <core.jsonl과 docs.jsonl이 함께 있는 디렉터리> \
  --k 5 --out data/generated/docs-v2/relabeled-docs-only.json
```

`--prepared`에는 `core.jsonl`과 `docs.jsonl`이 함께 있어야 색인 범위 문제와 순위
문제가 갈린다.

원자료는 `data/generated/docs-v2/`의 `evaluation-135q-docs-only.json`,
`evaluation-135q-core-docs.json`, `evaluation-135q-core-trim-docs.json`,
`evaluation-135q-core-rechunk-docs.json`과, 라벨을 고친 뒤 다시 잰
`relabeled-docs-only.json`, `relabeled-core-docs.json`,
`relabeled-core-rechunk-docs.json`이다.
