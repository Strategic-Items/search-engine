# 문서 파서 연동 — 2026-09-16

원본 문서(HWP/HWPX/PDF)를 파싱해 검색 색인에 넣는 경로를 붙였다. 파싱은
[`unstructured-doc-parser`](../../../unstructured-doc-parser)가, 임베딩과 색인·검색은
이 저장소가 맡는다.

## 연결 지점은 파일이다

두 저장소는 서로를 import하지 않는다. 파서가 `search-index`가 그대로 먹는 JSONL과
manifest를 쓰고, 이 저장소가 그 파일을 읽는다.

```
files/*.hwp|hwpx|pdf
  → parse_to_markdown() → chunk_markdown() → docs.jsonl + manifest.json   (파서)
  ──────────────────────────── 파일 ────────────────────────────
  → search-index docs.jsonl --dataset docs --manifest manifest.json        (이 저장소)
  → search-docs-v… (Ollama 임베딩 포함)
  → /v1/search, /v1/rag/stream 이 core와 함께 조회
```

코드 의존성을 두지 않은 이유는 방향이 한쪽뿐이기 때문이다. 파서는 검색 결과를 쓰지
않고, 검색은 파싱 과정을 알 필요가 없다. 파일 한 장이면 충분한 계약에 두 저장소를
서로의 빌드에 묶을 이유가 없다.

## 임베딩은 이 저장소가 소유한다

파서 쪽에도 임베딩(`BAAI/bge-m3`, 1024차원)과 pgvector 저장 계획이 스텁으로 있었으나
제거했다. 벡터 저장소가 둘이면 하이브리드 검색이 갈라진다 — BM25는 OpenSearch에,
벡터는 Postgres에 있으면 RRF로 융합할 대상이 애초에 한자리에 모이지 않는다.

그래서 파서는 청크 텍스트까지만 만들고, 벡터는 `search-index`가 색인 시점에
`embedding_text(title, body)`로 직접 만든다. 파서 쪽 폐쇄망 제약은 그대로 지켜진다 —
이 저장소도 로컬 Ollama만 호출한다.

## 왜 별도 데이터셋인가

`search-index`는 새 인덱스를 통째로 만든 뒤 별칭을 옮긴다. 즉 **입력 파일에 없는
문서는 사라진다.** 실습 코퍼스와 파싱 코퍼스를 한 인덱스에 합치면 어느 한쪽만 다시
만들 수 없고, 매번 양쪽 전부를 손에 쥐고 있어야 한다.

`docs`를 따로 두면 각자 독립적으로 재색인된다. 대신 검색은 두 인덱스를 함께 조회해야
하는데, 이건 `client.search(index=...)`가 쉼표로 구분된 인덱스 목록을 받으므로
별칭 문자열 하나로 끝난다(`Settings.document_aliases`). 질의 로직은 바뀌지 않았다.

`docs`는 `core`와 **같은 매핑**(`index_body`)을 쓴다. 분석기·동의어·벡터 차원이
같아야 두 인덱스를 한 질의로 조회할 수 있다.

두 인덱스를 함께 조회하면 BM25의 IDF가 인덱스별로 계산돼 어휘 점수에 편차가 생긴다.
다만 RRF는 점수가 아니라 순위로 융합하므로 영향은 제한적이다. 결과는 `parent_id`
기준으로 중복이 제거되고, 두 데이터셋의 `parent_id`는 겹치지 않는다.

## 색인되지 않은 인덱스는 조회를 깨뜨리지 않는다

`docs`를 한 번도 만들지 않은 클러스터에서도 쉼표 목록 조회가 실패하면 안 되므로
`ignore_unavailable=True`를 붙였다. 없는 인덱스는 결과를 좁힐 뿐 요청을 실패시키지
않는다.

여기에 한 가지 함정이 있다. **인덱스는 있지만 벡터 필드가 없는 경우**, k-NN 질의는
그 인덱스의 샤드만 실패시키고 HTTP 200으로 부분 결과를 돌려준다. 그러면 그 인덱스의
문서는 벡터 순위표에 아예 오르지 못하고, 두 순위표에 모두 오른 다른 인덱스 문서에
RRF로 밀려 사실상 검색에서 사라진다. 오류가 나지 않으므로 눈에 띄지도 않는다.

벡터 매핑 이전에 만들어진 인덱스가 별칭에 걸려 있으면 정확히 이 상태가 된다.
재색인으로 풀 문제이고 질의 버그가 아니지만, 보이지 않으면 고칠 수 없으므로
`_warn_on_partial_results`가 빠진 인덱스와 사유를 경고 로그로 남긴다.

## 파서가 채우는 필드

`SearchDocument` 계약을 그대로 따른다. JSONL 한 줄이 한 청크다.

| 필드 | 값 |
|---|---|
| `parent_id` | 원본 파일의 상대 경로에서 만든 slug + 경로 해시 8자리. 같은 파일을 다시 처리하면 같은 값이 나온다 |
| `id` | `{parent_id}#{청크순번:04d}` |
| `title` | 파일명에서 뽑은 문서 제목. 청크가 조항으로 시작하면 `— 제8조(…)`를 덧붙인다 |
| `body` | 청크 본문 |
| `source_type` | `공고문` |
| `published_at` | 파일명에 박힌 날짜(`(20260731)`, `(250923)`). 없으면 `null` |
| `date_basis` | `publication_only` 또는 `undated` |
| `content_hash` | `sha256("title\nbody\ncode")` — `search-prepare`와 같은 레시피 |
| `code` | 비어 있다 (아래 참고) |

`chunk_index`·`chunk_count`·`source_path`·`source_format`도 함께 들어가지만 매핑이
`dynamic: false`라 `_source`에만 남고 검색·필터에는 쓸 수 없다. 운영 중 원본을
되짚을 때만 쓴다.

제목은 비어 있을 수 없고(`min_length=1`) 본문의 3배로 가중되며 임베딩 입력에도
들어가므로, 청크마다 실제 내용을 가리키는 제목이 필요하다. 그래서 조항 표제를
덧붙이되 조문 본문 전체가 제목으로 딸려오지 않도록 조 번호와 괄호 표제까지만 자른다.

## 남겨둔 것

**관리번호(`code`)가 비어 있다.** 파싱된 공고문에도 `5D002` 같은 관리번호가 본문에
나오지만, 추출 정규식(`search_engine/codes.py`)은 이 저장소 소유다. 파서에 복제하면
파일 핸드오프로 얻은 분리가 무너지고 두 곳이 어긋날 여지가 생긴다. 검색 품질에
실제로 영향이 확인되면 `index_source()`에서 `body`로부터 뽑는 편이 옳다 — 그러면
실습 코퍼스에도 같은 이득이 돌아간다.

**내용 없는 표 조각은 앞 본문에 합쳐 넣는다.** 파싱된 표는 서명란처럼 빈 칸으로
이어져서 `| 산업통상부장관 | 직인 |` 같은 조각이 나온다. 첫 색인에서 이 조각들이
**모든 질의에 코사인 0.90으로 벡터 1위**를 차지하는 것을 확인했다 — 내용이 없으니
벡터 공간 중심 근처에 놓여 아무 질의에나 최근접 이웃이 되고, RRF에서 두 순위표에
모두 오르는 셈이 되어 진짜 답을 밀어낸다. 오류가 나지 않아 눈에 띄지도 않는다.
파서가 이런 조각을 버리지 않고 앞선 본문 청크에 이어 붙여 해결했다. 707청크.

**첫 적재에서는 HWPML 2건을 건너뛰었다.** 당시에는 확장자가 `.hwp`지만 실제 내용은
XML인 파일을 처리할 파서가 없었다. 최신 파서에서는 지원한다(아래 재검증 참고).
색인 전에 manifest의 `skipped`를 확인해야 한다 — 인덱스가 통째로 교체되므로
여기 적힌 문서는 곧 검색에서 빠진 문서다.

**PDF 페이지 번호가 없다.** 현재 파서가 페이지 경계를 버린다. 청크에 페이지를 달려면
파서 수정이 먼저다.

**개정 이력(`superseded_by`) 탐지가 없다.** `search-prepare`의 `supersessions()`는
실습 코퍼스의 별지·고시 차수 체계 전용이라 공고문에 그대로 쓸 수 없다.

## 최신 파서 연동 재검증 — 2026-09-16

파서의 `feat/search-corpus-export` 작업 트리에서 원본 전체를 임시 디렉터리에
다시 파싱했다. 기존 `data/chunks` 산출물과 서비스 별칭은 교체하지 않았다.

- 검색엔진 테스트: 88개 통과. 파서 테스트: 36개 통과.
- 원본 36건 → 부모 문서 36건 / 1,041청크. HWP5·HWPX·PDF·HWPML 모두 처리,
  `skipped` 없음. 게시일 있는 청크 372개.
- 검색엔진 `document_actions`로 전체 입력 검증 및 manifest 건수·SHA-256 일치 확인.
- 실제 `search-index --dataset docs --manifest ...`로 격리 테스트 인덱스에 적재.
  로컬 Ollama `nomic-embed-text` 768차원 임베딩과 OpenSearch 적재 건수 1,041개 확인.
- 공모전·청년인턴·할당관세·대외무역법 시행령·수출통관 5개 질의에서
  BM25/k-NN 샤드 실패 0건 및 `/v1/search` 공고문 반환, 부모 ID 중복 제거 확인.
- 기존 core와 통합 검색 및 `HSK 2826-9020-00` 연계표 조회 확인.
- 실제 RAG 검색 및 `/v1/rag/stream`의 Ollama 답변 생성 확인: HTTP 200,
  SSE `done` 수신, `error` 이벤트 없음. 생성된 답변의 사실성 평가는 별도다.
- 기존 `search-documents`·`search-docs` 별칭 유지 확인 후 테스트 인덱스만 삭제.

이 검증은 파일 계약과 실제 처리 경로의 동작 확인이다. 검색 관련도에 대한 정량
평가는 아니며, 서로 다른 원본 포맷의 동일 문서는 다른 부모 ID로 반환될 수 있다.
