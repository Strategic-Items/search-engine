## 1. 유진 — 비정형 문서 파싱 (PDF·HWP → 마크다운)

### 발표 내용
- **PDF**
  - 겹친 형태로 만들어진 폰트를 여러 번 읽어 글자가 반복되던 문제: 같은 크기 글자가 일정 비율 이상 겹치면 한 번만 읽도록 수정
  - 배경 없는 이미지는 투명 배경으로 저장, 너무 작은 이미지는 생략
- **HWP**: pyhwp(추정)만 쓰면 박스 안 표 구조를 못 읽고 단어 나열로 출력 → 박스는 원본 레코드 방식으로 내부 요소를 읽게 수정
- **유형별 청킹**
  - 법령 신구조문 대비표(현행/개정안): 양쪽 조 번호를 매칭해 같은 조문 단위로 묶고, 매칭 안 되는 신설 조문은 따로 묶음
  - 별지: 행 단위로 나누면 빈 표가 의미 없어 통째로 묶음
  - 민원 FAQ(임시 기준): 물음표로 끝나는 짧은 줄이 3개 이상인 문서는 질문 줄과 다음 줄 답변을 한 청크로 묶음
- 청킹 테스트에 **데이터 유실 검사**(원본 vs 마크다운 차이) 추가
- 이미지·마크다운 전문 추출 설정만 해둠. 이미지 설명 정보는 아직 없음. 청킹 시 이미지를 앞 문단이나 제목 뒤에 붙임
- 메타데이터: 법령고시만 이전 판본을 찾도록 이전 헤더 정보 추가. 본문에 단서 없는 문서가 많아 빈 값이 많음
- 법령고시 데이터: 전략물자 사이트 파일 + API로 약 50건 추가

### 피드백
- **지금 가진 데이터셋에 과적합하고 있다.** 핵심은 HWP·PDF를 원본을 보존한 채 MD로 잘 떨어뜨리는 것. 범용적으로 가고, 실데이터에서 생기는 예외는 그때 처리한다.
  - 물음표 기준 FAQ 파싱처럼 특정 형식에 맞춘 규칙은 다시 점검할 것. 문서를 많이 추가해 표가 정상적으로 내려오는지 확인
- **청킹은 검색 담당(정빈)의 일.** 파싱 쪽은 마크다운까지만 책임진다. 검색 요구로 앞단이 계속 흔들리면 모델이 바뀔 때마다 다 뒤집어야 한다. 마크다운 구조가 이상해서 청킹이 안 될 때 둘이 상의한다.
- 다음 발표에는 **변환된 마크다운 결과물(특히 표)**을 보여줄 것
- 무역안보관리원도 대부분 HWP이고 자체 라이브러리로 변환하지만 잘 안 된다고 함 → **HWP → HWPX/문서 변환 → 마크다운** 파이프라인 기준을 우리가 제시해야 한다
- 이미지는 경로만 남기지 말고 **VLM(sLLM)으로 이미지 설명을 뽑아 그 자리에 텍스트로 삽입**해야 검색된다 (예: 전략물자 허가 절차 플로우차트)
- AI 모델·GPU가 필요한 작업은 보고서 맨 아래 비고란에 적을 것 ("API로 해보고 싶은데 못 했다, 하루 할당해주면 해보겠다") → 사수가 GPU 일정을 조정해준다

## 2. 정빈 — 검색 엔진 구조와 카테고리별 검색

### 발표 내용
- **구조도**: 질문 → 날짜 포함 여부 판단 → 시행일·종료일, 공고번호·코드 필터 → BM25 / dense(BGE-M3-KO) / SPLADE 검색 → 각 컷오프 → RRF → RRF 후 컷오프(1위의 95% 미만 제외, 검색기별 1위는 보존, 문서당 최대 6청크) → 문서별 묶음 → 판정 LLM이 답변 여부 결정 후 RAG
  - BM25: 형태소 분석, 조사 등 제거, 제목·본문 가중치, 현행판·연월 일치 부스팅
  - dense: 절대 컷오프 0.7063 + 1위의 97% 미만 제거. dense가 전부 잘리면 다른 검색기 결과가 있어도 결과 없음 처리(도메인 밖 질문 차단)
  - BGE-M3와 KO 버전 비교 결과 한국어 학습판이 더 좋아 채택
  - 리랭킹·LLM 청크 관련성 판단은 옵션으로만 두고 이번엔 미사용
- **카테고리**: 법령고시 150건, 행정업무 20건, 민원 FAQ 19건
  - 법령고시: 문서 정확도 0.987(150건 중 1~2건 실패), 청크는 약 8건 실패
  - 메타데이터: 기간 필터, 공고번호 필터, heading path 입력 추가, 대체 여부(현행판 우선, 특정 연도 질문 시 해당 연도판 → 이후 개정판 순)
- **실패 사례**: 정답 청크가 SPLADE 4위, dense 5위로 밀림. 짧고 단어가 많은 청크가 1위로 올라옴 → RRF 컷오프에서 정답이 잘림
- **청킹 개선 요청 사례**: 잘려 있던 표 열(과태료 금액)을 넣어달라고 요청 → 검색 안 되던 질문이 1위로. 통제번호를 청크 앞에 넣었더니 점수 상승

### 피드백
- 표 열 복구 사례: 원본 데이터를 임의로 수정한 것처럼 보일 수 있다. 특화된 조건이 자꾸 들어가는 것을 경계할 것
- **통제번호는 청크 본문이 아니라 메타데이터에 넣어야 하지 않나?** 문서 메타데이터가 청크까지 따라가는지 확인하고, 메타데이터로 묶었을 때 순위가 오르는지 볼 것
- **컷오프를 이렇게 빡빡하게 걸면 안 된다.**
  - precision 수치는 중요하지 않다. RAG를 쓰는 이유가 정답이 컷오프로 잘리는 걸 막고 LLM에게 판단을 맡기기 위해서다
  - 점수가 정말 낮은 것만 버리고 나머지는 RAG에 넘길 것
  - 고시는 아래쪽에 예외 조항이 붙는 경우가 많다. 예외 조항이 잘리면 "수출해도 된다"는 잘못된 답이 나간다
  - 여러 청크를 조합해야 하는 멀티홉 질문(예: 특정 국가에 특정 품목을 수출해도 되나?)에서는 아래 순위 청크를 끌어와야 할 일이 많다
  - 개수는 지금 정할 필요 없음
- **어려운 질문으로 시험할 것**: 고시를 보고 직접 만든 질문 말고, AI 모델로 진짜 어려운 질문을 만들어 넣어볼 것. 또는 민원 FAQ를 색인에서 빼고 그 질문을 시험지로 쓸 것
- 전체 프로세스 재점검: 조건을 처음부터 단정적으로 걸고 있다. 정답이 왜 4위·5위로 밀리는지 이유를 보여줄 것. RRF 순위 조정 기준이 이해되지 않는다
- 질의를 더 다양하게 던져볼 것
- **지표에 대한 관점**: recall·precision 같은 수치는 검색 엔진 성능을 재기 위한 것일 뿐, 어느 정도만 나오면 된다. 중요한 건 실제 사용자가 써봤을 때와 RAG에 넘겼을 때 어떤 답이 나오는가다. 이 도메인은 "안 걸리면 말고"가 아니라 **못 찾는 게 가장 큰 리스크**다. 지금은 눈으로 확인하는 게 제일 중요하다

## 3. 수호 — 상담 녹취 STT 후처리와 검색

### 발표 내용
- 파이프라인: Whisper large STT → 용어집 보정 → LLM 전체 점검 → LLM으로 요약·Q&A·키워드 추출 → 문맥적 청킹 → 통화·청크 JSONL 출력 → BM25 + 임베딩 검색 → 모범 답안 생성
- **애매한 전사 교정**(예: 허가 기간 / 허가 기관): LLM에 교정 후보와 문맥을 함께 주는 방식 비교
  - 예/아니오로 답하지 않고 고칠 말도 주지 않은 방식이 가장 좋았지만 정상 문장을 일부 망가뜨림 → **기존 교정 규칙 유지**(띄어 쓴 두 단어가 모두 정상 명사면 고치지 않음)
- 일반 상담 샘플("담당자에게 문의하세요"로 넘기는 경우) 추가: 대체로 맞지만 없는 답을 지어내기도 함
- 검색 대상: 추출 요소만 넣은 것 vs 청크 원문까지 넣은 것 → 큰 차이는 없지만 원문 포함이 정답을 더 잘 찾음
- 300자 고정 청킹 vs 문맥적 청킹 → 문맥적 청킹 채택
- 상위 3개 청크 원문으로 LLM 모범 답안 생성 → 정답과 약 81% 일치(실패 22건). 판정은 Claude가 함

### 피드백
- 설명이 이해되지 않았다. "지금 방식"과 "채택한 방식"이 무엇인지 명확히 할 것
- **"정상 명사" 기준이 불분명하다.** 형태소 분석기가 명사로 판정하면 정상 명사로 보는 방식이면 대부분 명사로 판정될 것이다. 고유명사나 "허가 충협" 같은 오전사는 어떻게 판정되는지 확인할 것
- 형태소 분석 결과 → 용어집 적용 결과를 샘플로 정확히 보여줄 것. **용어집의 정체**(단순 단어 목록인지 유사어까지 포함한 정리본인지)를 보여줄 것. 용어집에 한쪽 단어만 있을 때와 둘 다 있을 때의 차이, 업데이트 여부에 따른 차이도 볼 것
- 지표 분모가 다른 이유(29·12 vs 30·18)를 설명할 것
- 지난 발표엔 캡처만 있고 설명이 없었는데 이번엔 설명만 있고 캡처가 없다. "원래 이렇게 청킹했는데 이렇게 바꿨더니 더 잘 됐다"처럼 화면으로 보여줄 것
- **실패 22건 재판정**: 질문 + 검색 결과 + 청크 원문을 LLM에 주고 "이걸로 답해도 되는지" 판정시켜 22건 중 몇 건이 걸리는지 확인 → **Slack에 공유**
- "검색 실패"와 "답 거절"의 정의를 구분할 것 (검색 실패 = 아무것도 안 나옴, 답 거절 = 데이터는 있지만 LLM이 답하지 않음)
- 추출한 Q&A는 고객 CRM의 문의/답변 메모란에 올리는 요구를 대체해도 큰 무리가 없겠다
